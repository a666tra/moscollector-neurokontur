# Происхождение данных, пайплайн обучения и двухуровневая воспроизводимость

## 1. Архитектура воспроизводимости решения

В проекте «Москоллектор.НейроКонтур» реализована строго документированная **двухуровневая схема воспроизводимости** (2-Tier Reproducibility Architecture):

```
┌────────────────────────────────────────────────────────────────────────────────────────┐
│ TIER 1: Полное сквозное воспроизведение от сырых данных (Среда разработчика/Сервер)   │
│                                                                                        │
│ [Сырой CSV организаторов 1.49 ГБ] (SHA-256: 4dbbb106...)                               │
│       │                                                                                │
│       ▼ FAST_CACHE=0 python backend/ml/train_validated_model.py                        │
│ 1. Проверка целостности SHA-256                                                        │
│ 2. Статическая фиксация реестра СМВУ (t=0, sensors_ref.json, 11 485 каналов)           │
│ 3. 3-way темпоральный сплит (Train < 14 янв, Val < 21 янв, Test < 28 янв)             │
│ 4. Алгоритмическая разметка proxy-таргета в окне горизонта [t+24ч, t+72ч]              │
│ 5. Извлечение 21 инженерного признака телеметрии                                       │
│       │                                                                                │
│       ▼ Выход: backend/data/extracted_features_cache.npz (SHA-256: 65871b3b...)        │
└───────────────────────────────────────────┬────────────────────────────────────────────┘
                                            │
                                            ▼
┌────────────────────────────────────────────────────────────────────────────────────────┐
│ TIER 2: Автономное воспроизведение в релизном пакете (Релизный ZIP / Жюри / Песочница) │
│                                                                                        │
│ [Кэш признаков extracted_features_cache.npz] (183 КБ, SHA-256: 65871b3b...)            │
│       │                                                                                │
│       ▼ python scripts/reproduce_metrics.py                                            │
│ 1. Загрузка Test split (N=11 485, 174 позитивных события, 1.51% редкого класса)        │
│ 2. Загрузка моделей и скалера (champion_lgbm, logistic_regression, random_forest)      │
│ 3. Расчёт ранжирующих метрик (PR-AUC, ROC-AUC, Lift)                                   │
│ 4. Применение beta-калибратора (обучен строго на Val split)                            │
│ 5. Расчёт калиброванных Brier Score и ECE (10 бинов) против константного baseline     │
│ 6. Проверка динамических инвариантов матрицы ошибок по 7 подсистемам                   │
│       │                                                                                │
│       ▼ Выход: backend/models/metrics_report.json                                      │
└────────────────────────────────────────────────────────────────────────────────────────┘
```

> [!IMPORTANT]
> **Почему в релизный ZIP включён Tier 2, а не 1.49 ГБ CSV:**
> Исходный файл `ext-journal-2026.csv` имеет объём 1 497 523 553 байт (~1.49 ГБ, 31 млн строк). Включение файлов такого объёма в релизный архив сделало бы невозможным быструю распаковку, проверку и передачу дистрибутива (превышение лимитов платформ хакатона).
> Поэтому релизный ZIP самодостаточен на уровне **Tier 2**: содержит предварительно извлечённый кэш признаков с контрольной суммой SHA-256, позволяющий за несколько секунд пересчитать и верифицировать все метрики, калибровочные кривые и матрицы ошибок.

## 3. Определение целевой переменной (Proxy-Target) и честные ограничения

### Что предсказывает модель:
Модель предсказывает **наступление критической телеметрической аномалии (предотказного состояния) СМВУ в горизонте от 24 до 72 часов** от момента формирования признаков:
1. **Сброс аппаратных часов контроллера (RTC epoch 1970):** симптом зависания микропроцессорного блока, просадки питания или сбоя микропрограммы СМВУ.
2. **Аппаратные отказы линий связи и датчиков:** явные системные маркеры `обрыв датчика`, `короткое замыкание`, `ошибка связи`, `сбой питания`.
3. **Предельная загазованность метаном:** концентрация $\text{CH}_4 \ge 5.0\%$ об. (100% НКПР — порог взрывоопасности и насыщения сенсора).
4. **Критический перегрев кабельных линий:** температура $\ge 45^\circ\text{C}$ в подземном коллекторе (угроза деградации изоляции силовых кабелей 10–220 кВ) либо аварийная разморозка $\le -10^\circ\text{C}$.
5. **Выход аналоговых сигналов за пределы физической достоверности** (out-of-bounds).

### Честные ограничения разметки:
1. **Отсутствие закрытых актов 1С:ТОИР:** В исходных данных организаторов хакатона не было внешних журналов фактического выезда аварийных бригад, дефектных ведомостей и актов списания оборудования.
2. **Алгоритмический proxy-характер:** Метка $y=1$ сформирована по телеметрии будущего периода, а не по физическому акту замены сенсора.
3. **Разделение риска и вероятности:** Сырой скор LightGBM (`risk_score`) ранжирует каналы по степени аномальности (PR-AUC 0.168, ROC-AUC 0.771). Откалиброванная вероятность (`calibrated_probability`) отражает истинную апостериорную вероятность наступления телеметрического инцидента с учётом базовой частоты 1.51%, но не заменяет факт выезда аварийной бригады.

## 4. Схема 21 физического признака (Feature Schema)

Каждый канал измерения описывается 21-мерным вектором признаков, вычисляемым строго по окну истории $[t-7\text{д}, t]$:

| № | Имя признака | Физический смысл | Источник расчёта |
|:---|:---|:---|:---|
| 0 | `cnt_24h` | Количество телеметрических посылок за последние 24 часа | Суточный счётчик |
| 1 | `cnt_7d` | Количество посылок за 7 суток | Недельный счётчик |
| 2 | `alarms_24h` | Число тревожных превышений (`тревожное=t`) за 24 часа | Суточный счётчик тревог |
| 3 | `alarms_7d` | Число тревожных превышений за 7 суток | Недельный счётчик тревог |
| 4 | `alarm_ratio` | Доля тревожных посылок в общем потоке за 7 суток | `alarms_7d / cnt_7d` |
| 5 | `acc_events` | Ускорение потока сообщений (активность 24ч vs среднее за 7д) | `cnt_24h / (cnt_7d / 7 + 0.1)` |
| 6 | `acc_alarms` | Ускорение потока тревог (всплеск за 24ч vs среднее за 7д) | `alarms_24h / (alarms_7d / 7 + 0.1)` |
| 7 | `chatter_cnt` | Число дребезговых переключений (смена состояния за $\Delta t < 60$ с) | Фильтр дребезга контактов |
| 8 | `chatter_ratio` | Доля дребезга в общем объёме недельного трафика | `chatter_cnt / cnt_7d` |
| 9 | `battery_glitches` | Число событий просадки резервного питания / батареи | Поиск ключевых слов питания |
| 10 | `date_corruptions` | Число сбросов даты в 1970 год (сбой RTC контроллера) | Поиск года 1970 в штампах |
| 11 | `unique_states` | Число уникальных состояний датчика за 7 суток | Мощность множества состояний |
| 12 | `silence_hours` | Время отсутствия посылок от канала до момента отсечки (в часах) | $(t - t_{\text{last}}) / 3600$ |
| 13 | `num_mean` | Среднее значение аналогового сигнала за 7 суток | `np.mean(numeric_vals)` |
| 14 | `num_std` | Среднеквадратическое отклонение аналогового сигнала | `np.std(numeric_vals)` |
| 15 | `num_max` | Максимальное значение аналогового сигнала за 7 суток | `np.max(numeric_vals)` |
| 16 | `sensor_type_code` | Категориальный код типа датчика по `sensors_ref.json` | Label encoding типа датчика |
| 17 | `system_type_code` | Категориальный код инженерной подсистемы | Label encoding подсистемы |
| 18 | `gas_spikes` | Число всплесков метана $\ge 1.0\%$ об. за 7 суток | Счётчик предупреждений загазованности |
| 19 | `temp_spikes` | Число температурных всплесков $\ge 35^\circ\text{C}$ за 7 суток | Счётчик нагрева силовых линий |
| 20 | `obj_level` | Иерархический уровень коллекторного узла (1–4) | По паспорту `objects_ref.json` |

## 5. Доказательство отсутствия утечки данных (Data Leakage Prevention)

1. **Строгое временное разделение:**
   - Момент среза Train: **14.01.2026 00:00:00**
   - Момент среза Validation: **21.01.2026 00:00:00**
   - Момент среза Test: **28.01.2026 00:00:00**
   - Истории датчиков формируются строго по событиям с датой $dt < \text{cutoff}$. Ни одно событие после момента отсечки не попадает в признаки.
2. **Изоляция окна целевой переменной:**
   - Окно целевой переменной начинается через 24 часа после отсечки ($t + 24\text{ч}$) и завершается через 72 часа ($t + 72\text{ч}$).
   - Буферное «слепое» окно в 24 часа гарантирует, что мгновенные кратковременные всплески в момент прогноза не создают тривиальной автокорреляции.
3. **Изоляция калибровки:**
   - Beta-калибратор (`champion_calibrator_beta.joblib`) обучается исключительно на паре $(X_{\text{val}}, y_{\text{val}})$; выбор относительно legacy Platt основан на OOF-проверке валидационной части.
   - Тестовая выборка Test используется один раз только для финального замера калибровочных показателей.
