# Москоллектор.НейроКонтур

Сервис прогнозирования инцидентов в инженерных коллекторах Москвы (ЛЦТ 2026, задача 8, АО «Москоллектор»).

Каждый день сервис ранжирует **11 485 каналов СМВУ** по вероятности инцидента в окне **24–72 часа**, показывает, какие признаки сработали, и готовит черновик заявки на ТО. Решение принимает диспетчер: выезд или ложная тревога, с причиной из справочника. Решения пишутся в журнал с цепочкой SHA-256; на пилоте они вместе с актами ТОиР пойдут в дообучение модели.

Два слоя: **быстрый контур правил** (газ, температура, пожар, затопление, дребезг, потеря связи — секунды и минуты) и **ML-прогноз деградации оборудования** на 24–72 часа. Интерфейс имеет две роли: техник («Поле», простые факты и что сделать) и диспетчер («Сводка», «Обстановка», «Заявки и журнал», «Качество модели», «Сценарии»).

## Результаты на реальных данных

Проверка на журнале СМВУ 2026 года, предоставленном организаторами (30,7 млн записей, январь–июнь). 21 недельный тест строго вперёд по времени: прогноз в среду 00:00 по истории до этого момента сравнивается с тем, что записано в журнале через 24–72 часа. Модель для недели k обучена только на неделях до k−1. **В работающем стенде стоит модель из второй строки** (обучена один раз в январе и не переобучалась); первая строка — расчёт для пилота.

| Медиана по 21 неделе | ROC-AUC | PR-AUC | Точность топ-50 | Точность топ-100 |
|---|---:|---:|---:|---:|
| **LightGBM с еженедельным дообучением** | **0,845** | **0,274** | **56 %** | **38 %** |
| Та же модель без дообучения (обучена в январе) | 0,648 | 0,142 | 34 % | 22 % |
| Логистическая регрессия, еженедельно | 0,792 | 0,197 | 48 % | 29 % |
| Правило «канал сбоил за последние 7 дней» | 0,704 | 0,181 | 48 % | 38 % |
| Случайный выбор (доля событий) | 0,5 | 0,013 | 1,3 % | 1,3 % |

Выводы:

- PR-AUC в ~20 раз выше случайного выбора, список топ-100 точнее случайного в ~29 раз.
- Модель без дообучения заметно слабее (ROC-AUC 0,648, точность топ-100 22 %) и по этим показателям уступает простому правилу «сбоил недавно». Поэтому в расчёте для пилота заложено еженедельное дообучение (ТЗ §8, «модуль дообучения»); в стенде оно не включено.
- Модель с еженедельным дообучением против правила за 21 неделю: по ROC-AUC и PR-AUC лучше в 18 неделях из 21; по точности топ-100 вровень (медиана 38 % у обоих: лучше в 8 неделях, хуже в 12, поровну в 1); в топ-200 уступает (24 % против 28 %).
- Главная ценность модели — каналы без сбоев за предыдущую неделю (59 % всех событий): правило «сбоил недавно» на них бесполезно (ROC-AUC 0,5), модель с дообучением даёт ROC-AUC 0,757, но точность топ-100 там мала (6 %), модель из стенда — ROC-AUC 0,578.
- Пересчёт всех 11 485 каналов — 62,86 мс, один канал — 1,5 мс (норматив ТЗ — 300 с на объект).

Полный отчёт: [`backend/models/rolling_backtest_report.json`](backend/models/rolling_backtest_report.json), в интерфейсе — вкладки «Сводка» и «Качество модели», в API — `GET /api/predictions/backtest`.

**Что считается событием.** В данных нет актов ремонтов (1С:ТОИР / CMMS), поэтому событие размечено по журналу СМВУ: состояние неисправности или отключения, сбой связи, сброс часов контроллера (1970), выход за физические пределы, опасные показания газа (CH4 ≥ 5 %) и температуры (≥ 45 °C). Правила — одна функция `is_failure_value` в [`backend/ml/features.py`](backend/ml/features.py). На пилоте разметка заменяется фактическими отказами из актов ТОиР ([методика](docs/DATA_REQUEST_AND_PILOT_METHODOLOGY.md)).

## Быстрый контур: Сценарный полигон

На реальных данных быстрых опасных событий почти нет, поэтому быстрый контур проверяется на **синтетическом** полигоне (185 каналов, сутки и месяц, сценарии S1–S8: медленная и быстрая утечка газа, перегрев, пожар, затопление, дребезг, потеря связи, колебание газа у уставки). Спецификация и пороги зафиксированы до первого прогона ([`docs/SCENARIOS_SPEC.md`](docs/SCENARIOS_SPEC.md)). Результаты на отложенных наборах (seed 2000–2019, 680 событий), прогнаны один раз:

| | Быстрый контур | Статический порог + дедупликация | Наивный порог |
|---|---:|---:|---:|
| События найдены | 680 из 680 | 600 из 680 | 600 из 680 |
| Ложные тревоги (всего за 20 наборов) | 1 | 80 | 80 |
| Оповещений в сутки (среднее) | 146 | 535 | 1 414 |
| Инцидентов в списке диспетчера | 67 | 502 | 1 414 |

Опережение фиксированного порога (медиана): утечка газа +6,9 мин, перегрев +37,3 мин. Колебание газа у уставки (замечание экспертов): 3 оповещения на событие против 15 у наивного порога.

Это проверка логики, не оценка на реальных авариях. Ложные тревоги статических вариантов вызваны заранее заложенными «нормальными» отклонениями (по построению теста); для потери связи у статических вариантов правила нет. В режиме «месяц» шаг замеров 5 минут, опережение по медленной утечке отрицательное (−2,6 мин): для пилота нужен опрос газа не реже раза в минуту. Результаты и версии кода: [`docs/SCENARIOS_HELDOUT_RESULTS.json`](docs/SCENARIOS_HELDOUT_RESULTS.json), пересчёт — `python tools/heldout_eval.py`.

## Быстрый старт

```bash
docker compose up --build
# интерфейс: http://localhost:8000, Swagger: http://localhost:8000/docs
```

Без Docker (Python 3.10+, Node 20+):

```bash
pip install -r requirements.txt
cd frontend && npm ci && npm run build && cd ..
python -m uvicorn backend.app.main:app --host 0.0.0.0 --port 8000
```

Windows: `run_local.bat`.

Облако: `render.yaml` — Render Blueprint (Docker, бесплатный план), стенд поднимается из этого репозитория без доработок.

**Учётка диспетчера.** Операции подтверждения тревог и нарядов требуют табельный номер и 6-значный PIN (PBKDF2-хэш). Для своей установки: `python scripts/provision_dispatcher.py --clearance-level 3 --can-confirm-false-alarm --can-force-dispatch`. Для публичного демо-стенда учётка создаётся из переменной окружения `LCT_DEMO_DISPATCHER_PIN` и показывается в интерфейсе.

## Возможности

| Требование ТЗ | Где в решении |
|---|---|
| Прогноз с вероятностью и горизонтом ≥ 24 ч | Экран «Обстановка» (диспетчер), «Поле» (техник), `GET /api/predictions` |
| Локация и тип объекта, классификация инцидента | Карта сети, объект, подсистема, тип датчика |
| Объяснение прогноза | Факторы риска по каждому каналу |
| Верификация и решение диспетчера с причиной | Фильтр тревог, `POST /api/alarms/confirm`, журнал с SHA-256 цепочкой |
| Рекомендации и черновики заявок ТО/ППР | Наряды, `POST /api/tickets/generate` |
| Настраиваемые параметры | Порог риска, окно и порог дребезга, порог газа, стоимость выезда/ТО, обязательность подтверждения — `GET/POST /api/settings` |
| Дообучение | Еженедельное переобучение проверено бэктестом (`scripts/rolling_backtest.py`); в стенде не включено — задача пилота |
| Быстрые опасные события (газ, перегрев, пожар, затопление, дребезг, потеря связи) | Быстрый контур, экран «Сценарии», `POST /api/scenarios/run` |
| REST API для интеграции | FastAPI, OpenAPI-схема `/api/openapi.json` |

## Архитектура

```text
Журнал СМВУ (CSV / API, только чтение)
  → backend/ml/features.py      21 признак за 24 ч и 7 дней: частота, тревоги, дребезг,
                                молчание канала, сбросы часов, числовые значения
  → LightGBM + beta-калибровка  backend/models/*.joblib
  → FastAPI (backend/app)       predictions · alarms · tickets · objects · settings · stats
  → быстрый контур правил       backend/app/services/scenario_engine.py (газ, температура, пожар, затопление, дребезг, связь)
  → React-пульт (frontend)      роль техника «Поле» · роль диспетчера: сводка · обстановка · заявки и журнал · качество модели · сценарии
  → журнал решений диспетчера   → еженедельное дообучение
```

Стек: Python 3.10, LightGBM, scikit-learn, FastAPI, Pydantic v2; React 18, TypeScript, Vite, Tailwind, Leaflet; Docker. Хранилище прототипа — JSON-файлы в `backend/data` (адаптер PostgreSQL — задача пилота).

```text
backend/app/        API и сервисы
backend/ml/         признаки (features.py), обучение (train_validated_model.py), бенчмарк API
backend/models/     модели и отчёты метрик
scripts/            бэктест, воспроизведение метрик, сверка, выдача учёток
tests/              108 автотестов (API, калибровка, бэктест, синтетический пайплайн, Сценарный полигон)
frontend/           интерфейс: роли техника и диспетчера
docs/               пояснительная записка, происхождение данных, методика пилота
tools/              сборка презентации и записки (не входит в сервис)
```

## Воспроизводимость

```bash
python -m pytest tests/ -q                   # 108 тестов
python scripts/rolling_backtest.py           # недельный бэктест из кэша признаков (1,6 МБ)
python scripts/rolling_backtest.py --extract # полный пересчёт из сырого журнала
python scripts/reproduce_metrics.py          # январский срез, калибровка, Top-K
python backend/ml/train_validated_model.py   # обучение модели
python tools/heldout_eval.py                 # отложенные наборы Сценарного полигона
```

Сырой журнал (`dataset/extracted/ext-journal-2026.csv`, 1,5 ГБ, SHA-256 `3ecdc8fcc5b08c8238fa74fadb35e9b6439bce3f2f8fe8697da5e483aae55880`) в репозиторий не входит — это файл организаторов. Кэши признаков в репозитории позволяют проверить все метрики без него; бэктест при запуске сверяет свои признаки для январских дат с обучающим кэшем (совпадение бит-в-бит записано в отчёте). Журнал не отсортирован по времени (около 0,7 млн разрывов порядка в июне), поэтому перед расчётом признаков он сортируется. Подробнее: [`docs/DATA_PROVENANCE_AND_REPRODUCIBILITY.md`](docs/DATA_PROVENANCE_AND_REPRODUCIBILITY.md).

## Границы прототипа

- Нет подключения к СМВУ, CMMS и AD/LDAP заказчика; интеграция описана через REST API в режиме только чтения.
- Метки — разметка событий журнала СМВУ, а не акты ремонтов; на пилоте переобучаемся на фактических отказах.
- Карта — схематичная топология и пикетаж без реальных координат.
- Быстрый контур проверен только на синтетических данных; на реальных авариях не проверялся.
- В стенде стоит январская модель без дообучения; она слабее простого правила (см. таблицу выше).
- Экономический эффект не измерен. В записке показано условие окупаемости: плановый осмотр (3 200 ₽) окупается, если доля подтверждённых проблем в списке не ниже 3 200 / 18 500 ≈ 17 %. Модель из стенда даёт 22 %, с дообучением — 38 % (по меткам журнала, а не по актам ремонтов).
